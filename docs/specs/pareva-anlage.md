# Spec: A Pareva Anlage is a product — Produkt-ID, and availability asked live

**Status:** implemented. Decisions 2 and 10 are superseded by `.scratch/schliesssysteme-ohne-menge/spec.md` (local, not committed): there is no „Menge“ (`accessPointDetails.accessPointAmounts`) any more, and `needed` is the booked units of the item, not `compartmentsAt`. The text below stays as history.
**Repo:** smart-city-booking-vue-app, branch `version/4.3.x`
**Backend:** changes required (smart-city-booking-backend, `version/4.3.x`) — see [Backend's share](#backends-share); the admin UI part can ship first, the wording does not depend on the backend.

## Problem

Since `457f577` ("Show an Anlage the one id field its provider reads") the access point dialog labels the `externalId` of a Pareva Anlage **"Produktgröße"**, with the hint "Ändern Sie die Produktgröße, um die Anlage bei Pareva auszutauschen." and a glossary row that calls it "the `size` of the Pareva product". That is the wrong word for the right value: the backend rents with it as the Pareva **product id** (`startRental(accessPoint.externalId)` → `POST /locker/{lockerId}/rental/{productId}/open`), and a product id at Pareva is a 24-hex object id such as `66570d1a1f9b6357ed971746`, not a size.

Two more things are wrong around it, both found while charting this change:

-   **The picker hands out size codes as product ids.** The backend's `ParevaAccessProvider.listAccessPoints` maps `GET /locker/{lockerId}/available` → `availableSizes[]` to access points with `externalId = size`. On a live cabinet that endpoint answers `{ size: "S", sizeName: "S", count: 11 }`, while the product the rental works with is `66570d1a…`. A Pareva Anlage taken over from the listing therefore stores `"S"` and would rent nothing. (Rows the fold migration made from the old `lockerDetails.units[].id` carry the hand-typed product id and are fine.)
-   **Nothing ever asks Pareva whether the product is available.** `ParevaCheckoutProvider` is registered but inert (`handlesAvailability: false`, `checkAvailability → { available: true }`). The only capacity is `bookable.amount`, which an admin has to keep in step with Pareva by hand. Before the locker fold the bookable editor had "Produkt-ID" + "Anzahl" per unit; the fold moved the number into the assignment table ("Menge" = Fächer je Buchung) and left the product's stock nowhere.

What Pareva is, in Marvin's words: a product has a stock at Pareva and lies in whichever compartment is free; the platform should not keep that number. A Pareva Anlage _is_ a Pareva product.

## Decisions

Numbered decisions come from the wayfinder map `.scratch/pareva-anlage-produkt-id/` (tickets 01, 02, 04, 06, 07) and two live calls Marvin made against a Pareva cabinet on 8 Sep 2026.

1. **Wording: "Produkt-ID".** Label "Produkt-ID", hint "Ändern Sie die Produkt-ID, um die Anlage bei Pareva auszutauschen.", glossary row "Produkt-ID (Pareva)". The word "Produktgröße" leaves copy, glossary, tests and the changelog's vocabulary. The translation keys are renamed with it (`productSize` → `productId`, `productSizeHint` → `productIdHint`); `providerIdFields("pareva")` points at the new keys.
2. **No amount on the Anlage.** A Pareva Anlage carries its Produkt-ID and nothing else that counts. "Menge" (`accessPointDetails.accessPointAmounts`, Fächer je Buchung) and "Stückzahl" (`bookable.amount`) keep their meanings; no third number, no "Kapazität".
3. **A Pareva Anlage is entered by hand.** The listing (`listAccessPoints`) lists sizes, not products, so it is no way into a Pareva Anlage. The picker ("Vom Anbieter übernehmen") offers only providers whose `providerCapabilities` include `listAccessPoints`; the backend drops that capability from Pareva (decision B1). The provider combobox of the form still lists every active provider, so "Manuell anlegen" with provider `pareva` is the way in; its help text says the id is the product's 24-hex id from Pareva's administration. Revises ticket 01 Q4 ("keep the picker") on the strength of ticket 04.
4. **Availability comes from Pareva, live.** The check is `POST /locker/{lockerId}/rental/available?v=2` with `{ productId, begin, end }`; Pareva answers one `ProductAssignment` per free compartment of the product in the window (each `stock: 1`), so **free = number of entries**. Not `GET /available` (keyed by size codes, its `count` unused).
5. **Both checks must pass.** The platform's own count against `bookable.amount` (`runAvailabilityCheck`) _and_ Pareva's answer. Today an external provider that handles availability replaces the internal count (iFBS); for Pareva the provider **narrows, never replaces**. iFBS is unchanged.
6. **Pareva unreachable → the platform count decides.** On timeout (10 s), a non-2xx answer or an unreadable body the Pareva check answers "unknown"; the booking then passes only if the internal count still has room. Never a hard refusal because Pareva is down, never a pass the platform count would not give.
7. **The checkout-to-payment gap is accepted.** Pareva cannot see unpaid bookings — the rental is started at `pay` (`grantAuthorization`), before that the compartment is held by the stored booking alone. `bookable.amount` stays, as today, the admin's per-bookable mirror of the product's stock and covers that window; the residual race between two bookables sharing one product is accepted. An expiry for unpaid bookings is out of scope.
8. **The Produkt-ID reaches the checkout through the assignment.** No `externalProviders` entry, no model hook (unlike iFBS' `bookable-ifbs-provider.js`). The checkout derives "this bookable has a Pareva Anlage" from `accessPointDetails.accessPointIds` → rows with `provider: "pareva"` → `externalId`, one check per product.
9. **It runs everywhere the seam runs.** `ItemCheckoutService.checkAvailability` is the one availability seam — storefront calendar, both checkouts, admin booking paths, block periods — so the Pareva check runs in all of them, cached per product + window inside one check (`_sharedCached`, the iFBS pattern).
10. **Compartments per booking are unchanged.** A booking still starts one rental per compartment (`compartmentsAt`); the availability check asks once per product and compares the entry count with the compartments the booking needs at that product (`compartmentsAt(bookable, row.id, itemAmount)`).

## Backend's share

For the backend session on `version/4.3.x`. Each item names the file it lands in; the backend keeps its own spec, changelog and `CONTEXT.md` conventions.

-   **B1 — Pareva lists no access points.** `ParevaAccessProvider`: remove `listAccessPoints` and take it out of `static get capabilities()`, so `AccessInfoService.getActiveProviders` reports Pareva without it and the admin UI hides the picker (decision 3). `ParevaApiClient.listSizes`/`getLocations`/`getLocationById` stay for `testConnection` and the legacy `/locker` routes. Contract test `tests/access-provider-contract.test.js` and the dialects test lose their Pareva `listAccessPoints` cases.
-   **B2 — Availability call.** `ParevaApiClient.getAvailableAssignments(productId, begin, end)` → `POST /locker/{lockerId}/rental/available?v=2`, body `{ productId, begin, end }` (epoch ms). Returns the array; the caller counts. Same `_request`, same 10 s timeout, errors rethrown.
-   **B3 — The Pareva checkout provider does the check.** `ParevaCheckoutProvider`: `handlesAvailability: true`, a new getter `narrowsAvailability: true` (default `false` on `BaseCheckoutProvider`; iFBS keeps replacing). `checkAvailability()` reads the product ids of the bookable's Pareva rows (decision 8: `accessPointDetails.accessPointIds` → `AccessPointManager.getAccessPointsByIds` → `provider === "pareva"`), calls B2 once per product via `_sharedCached("pareva:<lockerId>:<productId>:<begin>-<end>")`, and answers `{ available: entries.length >= needed, remaining: entries.length, externalSource: "pareva", productId }` where `needed = compartmentsAt(bookable, row.id, this.amount)`. Any failure (throw, non-array body) answers `{ available: null, unknown: true, message }` and logs a warning — no throw (decision 6).
-   **B4 — The seam runs both.** `ItemCheckoutService.checkAvailability()`: run `runAvailabilityCheck(...)` whenever the bookable has no _replacing_ external provider; then, for providers with `narrowsAvailability`, run their check and fail with the existing `CHECK_TYPES.AVAILABILITY` shape when one answers `available: false`; treat `unknown: true` as pass (the internal result stands). `hasExternalAvailability` on the bookable entity stays about `externalProviders` (iFBS); the Pareva provider is resolved from the rows, not from a declaration — `_resolveExternalProviders` gains a second source: one `ParevaCheckoutProvider` when the bookable references a Pareva row and the tenant's Pareva app is active (client via `createClient(app)` as today).
-   **B5 — Calendar and validate paths** need no change of their own: they already build an `ItemCheckoutService` (decision 9). Verify the per-check cache keeps the Pareva calls to one per product and window per calendar render.
-   **B6 — Misconfigured rows.** A Pareva row whose `externalId` is not a 24-hex id (a size code created through the picker after the fold) is misconfigured. On `holdForBooking`/`grantAuthorization` it fails at Pareva anyway; add a log line at B3 naming the row (`accessPointId`, `externalId`) when the availability call answers 404/400, so the admin can fix the Produkt-ID. No migration: nothing can guess the product id from a size code.
-   **B7 — Docs.** `CONTEXT.md` **Schließfachanlage**: "bei Pareva ein Produkt (Produkt-ID) einer Schließfachanlage; die Verfügbarkeit des Produkts fragt der Checkout live bei Pareva ab" and drop "size". `docs/entities.md` §AccessPoint: "a Pareva product" instead of "a Pareva size". Changelog entries for B1–B4.

## Acceptance criteria

-   Creating an access point with provider `pareva` shows one id field labelled "Produkt-ID" with the hint above and no "Standort-ID beim Anbieter"; editing a stored Pareva Anlage shows the same field, and the word "Produktgröße" appears nowhere in `src/`, `tests/` or `docs/agents/` (this spec and the changelog's history line keep it as the record of what changed).
-   With Pareva as the only active provider the dialog opens on "Manuell anlegen" with `pareva` preset and no switch; with Nuki and Pareva active the switch is offered and the picker's provider select lists Nuki only.
-   A saved Pareva Anlage stores the typed 24-hex id as `externalId`, `providerLocationId: null`, `type: "locker"`, `mode: "authorization"`, `validationRules: []`.
-   The management table shows a Pareva Anlage as "Selbst angelegt".
-   Backend, with B1–B4: `GET /api/:tenant/access-apps/providers` reports Pareva without `listAccessPoints`; a checkout of a bookable with a Pareva Anlage calls `rental/available` once per product and window, refuses when Pareva answers fewer entries than compartments needed, and — with Pareva unreachable — behaves exactly as today (platform count only). iFBS bookables behave exactly as today.
-   `npm run lint:check`, `npm run format:check` and `npm test` pass in the admin UI; the backend's contract and characterisation suites pass with the Pareva listing cases removed.

## Out of scope

-   An expiry for unpaid bookings (would close the gap of decision 7) — a booking-lifecycle effort of its own.
-   `GET /locker/{lockerId}/available` and its `count` — not the chosen check; it stays what `testConnection` uses.
-   The iFBS Anlage ("Standort-ID") and its checkout provider — untouched.
-   A products listing from Pareva (the API doc has none) and prefilling the Produkt-ID — revisit if Pareva documents one.
